# Learning plan: IS1200 Lab 4 Processor Design

## Teaching contract

Build one coherent route from instruction bits to state changes. Every activity should make the learner predict, set, or trace a value that a processor component determines, then show the path and explain the rule. Keep **Lab 4** as the default scope: `add`, `addi`, `beq`; eight 32-bit registers addressed by the low three address bits; `x0` hardwired to zero; combinational reads and rising-edge writes. Put `lw`, `sw`, `and`, `or`, `slt`, `ImmSrc`, and data memory behind a visibly labelled **Lecture 9 extension** boundary. Do not imply that the Lab 4 circuit implements them.

The supplied lab specifies contracts and test behavior, not a canonical factorial listing or a canonical `test.S` listing. Any short trace used to teach individual instructions is a generated/illustrative exercise, not quoted course code. For factorial, let the learner enter or import their own program; never present one invented implementation as the required solution. The lab's required factorial constraints are authoritative: input in `t0`, result in `t2`, only `add`/`addi`/`beq`, only registers 0–7, and a self-looping stop. Test at least 0!, 3!, and 8!.

## Progression

1. **Orient: what changes, what waits?** Start with a guided timeline separating combinational signals from state. Learners classify edits to A1/A2, read outputs, ALU inputs/result, WE3/WD3, clock edge, and register/PC state. Reveal propagation paths immediately; commit state only on a rising edge. This gives later traces a shared mental model.
2. **Read the instruction fields.** Begin with named fields and bit-range highlights rather than raw-bit recall. Learners select `rs1`, `rs2`, `rd`, opcode, and immediate from `add`, `addi`, `beq`; then place fields on a 32-bit strip and identify common positions. Introduce exact encodings and signed immediates only after the field roles are understood. B-type immediates need a dedicated assembly rule; never depict them as a contiguous 12-bit slice.
3. **Register file: address versus data.** Let learners set A1/A2 and predict RD1/RD2, then set A3/WD3/WE3 and choose whether a rising edge changes state. Show x0 reads as zero and ignore writes to x0. Use explicit labels so rs1/rs2/rd (instruction fields), A1/A2/A3 (addresses), and RD1/RD2/WD3 (data) cannot be confused.
4. **ALU: operands, operation, result.** Learners choose A, B, and F; calculate Y and Zero. Start with addition/subtraction and signed comparison, then bitwise operations as supported ALU knowledge. Make `A-B = A + ~B + 1` inspectable, including conditional B inversion and carry-in. Format values as decimal/hex/binary. Clarify Zero is meaningful for ADD/SUB in the lab contract; the control logic consumes it for branch comparison.
5. **Control unit: instruction to controls.** Given each supported instruction, learners set RegWrite, ALUSrc, Branch, and ALUControl, and explain the source of each. Then trace opcode/funct decoding to outputs. Explicitly distinguish encoded opcode/funct3 from generated ALUControl. Use distractors that test the distinction rather than memorization alone.
6. **Datapath trace: one instruction, one path.** This is the main practice mode and hub. Guided traces reveal one unknown at a time: decode fields → register reads/immediate → controls → mux choice → ALU/Zero → writeback and/or next PC → edge update. The diagram highlights active wires and annotates their values; each answer has a “why” explanation tied to the responsible component. Start with `addi`, then `add`, then `beq`; progress to mixed traces and fade hints. Include both correct and incorrect branch outcomes.
7. **Branch and PC decision.** Focus on `beq`: Branch marks the instruction class; `Branch AND Zero` determines taken. Learners compute SUB, Zero, PC+4, branch target, and PCnext. Include taken/not-taken cases and negative offsets. A separate short ROM-address task maps byte PC to word index (`PC >> 2`), including `0x0C → word 3`; connect this to fetch in the main trace.
8. **Encoding practice.** Assembly ↔ fields ↔ encoded bits/hex in graduated rounds: family/opcode, named operands, field placement, binary, then hex. Keep instruction forms within the three Lab 4 instructions. Provide worked correction for common field and immediate errors; avoid rewarding blind bit memorization before learners can explain fields.
9. **Factorial program workbench.** Provide editable/importable assembly under the lab's restrictions and single-step it using the canonical processor model. Show PC, fetched word, source line, registers, changed state, and branch decision. Learners predict `t2` over a selectable number of steps and run the required inputs. Validate restrictions and stop-loop presence; distinguish assembly-algorithm failures from datapath failures. Do not preload an allegedly canonical solution.
10. **Oral exam and review.** Short spoken-style prompts cover the lab's listed oral topics: register clocking/capacity, x0, ALU/subtraction/Zero, control signals, `beq`, bit selection, PC+4 and ROM indexing, ALUSrc, why the lab needs no ImmSrc for its bounded PC/offset case, factorial, and unconditional jump via `beq zero,zero,label`. Use concept-based checks for constrained answers; for explanation prompts, reveal model concepts and let learners self-assess instead of pretending brittle keyword matching is authoritative.

## Interaction and feedback rules

- Prefer manipulation and prediction: choose registers, controls and calculated values, place a field, step the clock, or predict state. Native choice lists support keyboard and touch; numeric questions also allow typed values.
- Let a learner revise a wrong value before advancing. On submission, show the expected value, the determining rule/component, and the consequence downstream; highlight that path in the diagram.
- Keep “current” and “next” values side by side. Combinational changes propagate before the edge; PC/register writes commit on the rising edge.
- Use stable, numbered series of bounded variants from legal instruction semantics, with readable values and immediate alignment/range checks. Keep each exercise's answer derived from the same processor model as the simulator.
- Offer Practice, Guided lesson, Oral exam and a Progress page. Save solved/reviewed task identities and cursors in a local cookie; let learners advance with Next exercise, revisit individual tasks, and explicitly reset their history. Keep prediction-accuracy statistics separate from completion.
- Use a single persistent datapath vocabulary and diagram. Labels, data buses, controls, and clocked state need distinct visual treatments and a compact legend.

## Source-grounded scope notes
